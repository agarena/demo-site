慢速缓存 · SLOW CACHE

造轮子·2025-11-30·约 6 分钟·沈知远

把博客首屏压进 300ms：一次性能考古

今年三月，这个博客的 Lighthouse 性能分是 45。六周之后，它变成了 98，首屏渲染压进 300 毫秒。这不是一篇教程，更像一次考古——把地一层层挖开，把挖出来的东西按出土顺序摆好；至于结论，你自己拿。

「性能优化做到最后，优化的不是分数，是对访客时间的基本礼貌。」

一、案发现场：45 分

出土的第一层是耻辱：一个以文字为主的博客，首屏要下载两套共 1.4MB 的字体、一份图标字体，外加三段没有 defer 的脚本，LCP 4.2 秒。也就是说，访客在看到标题之前，够泡半杯茶。

Lighthouse 性能分
45 → 98
LCP 最大内容绘制
4.2s → 1.1s
首屏渲染
1.9s → 0.31s
字体总体积
1.4MB → 84KB

分数只是症状。真正的病灶都写在上面的表里：字体、脚本，和「反正用户有 5G」的傲慢。

二、字体是最大的嫌疑人

统计之后发现，全站正文只用到了 1214 个汉字，而全套 Noto Serif SC 有两万多个字形——为了千分之一的使用率，付了百分之百的运费。

子集化之后，再配上行内 @font-face 和 font-display: swap，文字再也没有白屏过。有位读者留言说「你这站像换了台服务器」——其实只是把不该运的货卸了。

三、关键 CSS 内联

第二刀砍向渲染阻塞。把首屏要用的约 200 行 CSS 直接写进 head，其余样式在 load 之后异步注入。首屏渲染从 1.9 秒降到 0.31 秒——浏览器拿到 HTML 的那一刻，页面就已经是可读的了。

顺带清了三段第三方脚本里的两段：统计换成自托管的 3KB 版本；「友链预览」砍掉之后，没有任何人发现它不在了。

四、剩下的 2%

从 98 到 100 需要的力气，比从 45 到 98 还大，而且大部分和真实体验无关。我把力气留给了另一些事：图片全部懒加载、字体预加载，以及把正文行高调到 2——快，是为了让人读得慢。

考古结束。铲子留在这儿，下一座土堆见。

慢速缓存宣言：为什么我决定写得慢一点

这篇放在「半成品」栏目里，成熟度标记是「半成」——宣言嘛，就该永远是半成品；写完的那天，它就死了。

「慢速缓存，长期保鲜：把值得想的事，写在会呼吸的页面上。」

一、快是默认值，慢要自己争取

信息流替我们决定看什么，热点替我们决定想什么，日更的博主替我们决定大家应该多勤奋。快是这片互联网的默认值，而且没人征得我们同意。既然是默认值，那就意味着：想慢下来，得自己动手改配置。

二、三条原则

本站的底层协议只有三条，从 2024 年冬天开始执行——

  1. 一篇文章至少睡两晚。睡过之后还想发的，才值得发；
  2. 只写半年后自己还愿意搜到的题目。追热点的文字，保质期比酸奶还短；
  3. 读者可以等，评论可以晚回。桌上的仙人掌三个月没浇水都活得好好的，一个好博客不会因为周更而枯死。

三、把折腾写成可供检索的思考

白天写组件，晚上写句子。折腾是输入，写作是缓存：把一次性的折腾，变成可检索、可复用、三年后还能被搜索引擎捞出来的思考。这个站就是我的公开笔记本——字写得慢，但每一页都编号。

「缓存的意义从来不是快，是下次还找得到。」

这篇会一直挂着「半成」的标记。等哪天我觉得它把话说尽了，再把它改成「过时」。
