把博客首屏压进 300ms：一次性能考古

Lighthouse 从 45 到 98 分：字体子集化、关键 CSS 内联与「删库」式瘦身实录。完整 Lighthouse 数据表见文末附录说明。

① 起点：一张 45 分的截屏

事情始于一盆冷水。七月末我把新版博客部署上线，兴冲冲地打开 Lighthouse，跑出来的分数是 45。更难受的是我连续三次归因错位：第一次怪图片——可首屏根本没有几张图；第二次怪服务器——TTFB 稳定在 80ms，谈不上无辜但也不至于背全锅；第三次我怪构建工具——直到我把打包产物摊开在地上，发现罪魁祸首在镜子里：我自己。

移动端模拟跑分下，FCP 3.8s、LCP 4.6s、TBT 620ms。首屏请求 27 个，其中 6 个是字体、4 个是「以防万一」的 JS 库。这篇文章就是那份考古报告：我是怎么一锹一锹，把首屏从 3.8 秒挖回 0.9 秒的。

② 字体：从 6 个请求到 2 个

中文 webfont 是首屏杀手。我原来整包引入了两套字体，每套被浏览器切成几十个 unicode-range 分片，光字体就发起了 6 条以上请求，还互相阻塞渲染。做了三件事：

  • 用子集化工具把常用字压缩到 3500 字以内，全量字体从 4.2MB 压到 0.9MB；
  • 对比了三款子集化方案，最后选了按自有语料频率而非通用字频表切片的那款——博客正文的高频字和新闻语料并不一致；
  • 正文用系统字体栈兜底，品牌标题字体才走网络，并用 font-display: swap 保证文字永不白屏。
方案产物体积分片数备注
整包引入（原方案）4.2MB浏览器自动分片首屏 6+ 请求
通用字频表切片1.1MB90 片通用，但偏书面语
自有语料频率切片（采用）0.9MB60 片正文命中率最高

最终字体请求 6 → 2，且全部异步。这一项单项把 FCP 拉快了约 700ms。

③ CSS：14KB 的关键路径

我把首屏真正用到的样式手工抽出来——reset、排版、通知条、刊头——内联成 14KB 的关键 CSS 直接放进 <head>；其余全部走 media="print" 技巧延后加载（浏览器会以低优先级下载，加载完再切回 all）。这个老技巧到 2026 年依然好用，而且零依赖。

④ 图片：首屏 0 图策略

改版上线时我做了个激进决定：首屏不放任何位图。英雄区的背景是程序化绘制的 Canvas 星空，文章缩略图全部懒加载并预置同尺寸骨架屏，禁止布局抖动。LCP 元素从「一张装饰图」变成「标题文字」，直接提前到 1.2s——文字渲染永远比图片快，那就让文字当主角。

⑤ JS：删掉三个「以防万一」

考古最爽的部分来了。我删掉了三个库：一个轮播库（全站只有一处用过，改成了 30 行 CSS scroll-snap）、一个日期库（只用到了格式化，手写 12 行够了）、一个「以后可能会用」的图表库（对，它加载了八个月，一次都没被调用）。事件委托替代了原来的滚动监听轮子。首屏 JS 从 318KB 降到 96KB，gzip 后刚好卡进 150KB 的红线以内。

⑥ 终局：98 分与未完清单

最终截图：98 分。FCP 0.9s、LCP 1.2s、TBT 40ms、CLS 0。但考古笔记的最后一页我留了份未完清单：Service Worker 离线阅读、文章页按需字体的进一步切片、以及把首屏压进 300ms 的最后一口气——目前 TTFB 占掉了其中 80ms，剩下的 220ms 我还想再抠一抠。下篇见。
